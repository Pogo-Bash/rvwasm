# wlserver: the window server of the page

A Wayland compositor for the machine, written in JavaScript and run by the
browser's own engine as a process of the machine (the hostnode way:
`HOSTNODE_HOME=/run/wlserver hostnode`; boot.js says how). Its clients are
the riscv64 programs under the emulator (Qt, GTK, weston's demos, Xwayland
later); their windows are drawn by the page, from the machine's memory.

    debian desktop wayland konsole        (tools/x/desktop)
    debian desktop wayland konsole        (again: a second Konsole joins the server)
    debian desktop wayland kate           (Kate goes into the background; the server stays)

The parts: `boot.js` (memory, system calls, loading), `protocol.js` (the
protocol's tables, generated by `tools/wayland-scanner.js` from
`protocol/*.xml`), `wire.js` (messages in and out of a socket), `table.js`
(the surface table below), `compositor.js` (surfaces, buffers, what the
table says of them), `shell.js` (windows: xdg-shell, decorations, the page's
orders), `seat.js` (keyboard, pointer, focus, the pointer's picture),
`keyboard.js` (layouts and the modifiers' state), `data.js` (the clipboard,
the bridge to the host's, files from the host), `drag.js` (drag and drop),
`apps.js` (the programs for the panel's launcher, and starting one),
`layershell.js` (layer surfaces: zwlr_layer_shell_v1, plasmashell's desktop and panels), `plasmashell.js` (Plasma's protocols: plasma shell surfaces, window management for the task manager and pager, virtual desktops, output order, and the effects' protocols taken as no-ops), `textinput.js` (text from the host's input method: zwp_text_input_v3, for
Japanese, Chinese, Korean and the like), `x11.js` (the X11 protocol, a client's side), `xwm.js` (X programs:
Xwayland started on demand, and the X window manager), `xselection.js` (the
clipboard between X and Wayland programs), `server.js` (the socket, the clients, the turns: woken by the page's
doorbell, see Input, or every 8 ms without one). `keymaps/` has the
keyboard layouts as compiled XKB keymaps (`tools/wl-keymaps.sh` makes them:
`xkbcli compile-keymap` of libxkbcommon-tools 1.7.0 run under rv in the build
VM, with xkb-data 2.42 as in the Debian root; 30 layouts, 2 MB). The page's
side is `tools/www/display.js`, `tools/www/chrome.css` and
`tools/www/panel.css`.

`desktop wayland PROGRAM` starts the server if it does not run, gives the
program a session bus of its own (dbus-run-session) and the environment
(`QT_QPA_PLATFORM=wayland`, `XDG_SESSION_TYPE=wayland`,
`QT_QUICK_BACKEND=software`, `LIBGL_ALWAYS_SOFTWARE=1`,
`XDG_CURRENT_DESKTOP=KDE`, no `GDK_BACKEND`); when the program it started the
server for has ended, the server stays until its last client has been gone
for ten seconds. Whether a server runs is told by its lock: it holds an
flock on `$XDG_RUNTIME_DIR/wayland-0.lock` while it runs. (The script is the
staged one: stage.sh puts `tools/x/desktop` next to the server, and
debian-enter binds it over the disk's `/usr/local/bin/desktop`, which is as
old as the disk.)

## How pixels get to the page

A client's `wl_shm_pool` is a file in memory (a memfd stand-in, in a ramfs).
The server maps it shared, and on this kernel (no MMU) the address it gets is
where the file's pages are in the one linear memory of the machine. The page
has that memory too (`window.linuxOs.memory`): it uploads the damaged
rectangles of a buffer straight from there into a WebGL texture. Nothing is
copied in between.

Two things make that work and are worth knowing:

- The kernel gives a ramfs file contiguous pages only when it is truncated up
  from size 0 (fs/ramfs/file-nommu.c); a file grown any other way cannot be
  mapped shared (`mmap` says ENODEV). weston's and Xwayland's
  `os_create_anonymous_file()` grow the file with `posix_fallocate()`, which
  glibc emulates on a file system without `fallocate` by writing a byte into
  every block. So rv's `fallocate` (rv/syscall.c, `sys_fallocate()`) falls
  back to `ftruncate` when the host has none and the call only asks for room.
  A pool that cannot be mapped all the same is not an error here: its buffers
  are copied out of the file with `pread` on every commit, and the table
  points at the copy. That happens to every pool grown after its first
  mapping (`wl_shm_pool.resize` after `ftruncate`): libwayland-cursor grows
  its cursor-theme pool that way (seven doublings, 11792 to 981488 bytes,
  seen with weston-flower and weston-terminal), and the client's side of such
  a pool is then rv's `live_attach()` (a private copy written back to the
  file only on msync, munmap or exit), so the copy the server reads can be
  behind. Window pools are not resized by the clients seen so far and map
  directly on both sides. Cursor images are for M2 (`wl_pointer.set_cursor`);
  this is where to look if they come out blank.
- Buffers are released (`wl_buffer.release`) as soon as the page says it has
  uploaded the present they were attached for, and frame callbacks fire when
  the page says it has shown it. A double-buffered client therefore runs at
  the page's frame rate, one present per frame.

## The surface table

A struct in the server's memory, announced on `BroadcastChannel("rv-display-ID")`
(ID: the page load's id, `rvtab=ID` on the kernel's command line, read by `boot.js` from `/proc/cmdline`; plain
`rv-display` where there is none, as under `tools/node-machine.js`; the other channels, `rv-plasma`, `rv-gpu`, `rv-host`
and `rv-blenderweb`, are named the same way) as `{ type: "table", address, pid, slots, slotSize, header, width, height,
scale, version, layouts }` at start and once a second (`layouts`: `[{ name,
description }]`, the keymaps there are). All words are 32-bit little-endian; "page" marks
the words the page writes, everything else is the server's. The page
re-validates the magic and the pid every frame and treats a heartbeat that
has not moved for 2 s as a dead server.

Orders (what the page asks of the window `id`): 1 activate (raise, the
keyboard to it); 2 move (a, b: where its window geometry's top left corner is
to be); 3 resize (a: the edges dragged, xdg_toplevel's numbers: 1 top, 2
bottom, 4 left, 8 right and their sums; b, c: the geometry's size wanted:
the server configures the client with the `resizing` state, and keeps the
opposite edges where they were); 4 resize done; 5 close (xdg_toplevel.close);
6 minimize; 7 maximize or restore; 8 restore a minimized window (and activate
it); 9 fullscreen or not; 10 launch (id 0, a: an index in the apps list,
b: that list's apps_serial); 11 to 21 are Plasma's shell's (keep above and below,
shade, desktops, set the geometry, quick tile, show the desktop:
PLASMA-PROTOCOL.md). The page sends at most one move and one resize per
window per frame, and the server holds a configure back until the client
has acknowledged the one before.

Slot (384 bytes, slot `i` at `address + 2048 + i * 384`):

| offset | field | meaning |
| --- | --- | --- |
| 0 | seq | odd while the server writes the slot, even otherwise (read again if odd or changed) |
| 4 | id | the surface's number, unique while the server runs; 0: the slot is free |
| 8 | parent | a subsurface's (or a popup's) parent surface id, else 0 |
| 12 | kind | 1 toplevel, 2 popup, 3 subsurface, 5 a drag's icon (at the pointer), 6 a layer surface (plasmashell's desktop and panels: layershell.js) |
| 16, 20 | x, y | where the buffer's top left corner goes, in screen pixels; a subsurface: relative to its parent (popups: on the screen) |
| 24, 28 | w, h | the surface's size (the buffer's size over its scale) |
| 32 | z | the order to draw in, 0 lowest |
| 36 | flags | 1 mapped, 2 activated, 4 maximized, 8 fullscreen, 16 resizing, 32 decorated (the page draws its frame), 64 minimized (not drawn) |
| 40..56 | geometry | the window geometry (`xdg_surface.set_window_geometry`): x, y, w, h within the surface |
| 56 | present_id | +1 per commit that has something to show; what the page is to catch up with |
| 60, 64 | buffer_lo, buffer_hi | the pixels' address in the machine's memory |
| 68 | stride | bytes per row |
| 72 | format | 0 ARGB8888, 1 XRGB8888 (`wl_shm` formats: little-endian words, so bytes B, G, R, A); from dmabuf.js also 2 a GPU resource (buffer_lo the resource, buffer_hi the GPU server's pid: the page draws the GPU executor's texture), 3 ABGR8888, 4 XBGR8888 (bytes R, G, B, A) |
| 76, 80 | buf_w, buf_h | the buffer's size in pixels |
| 84 | scale | the buffer scale |
| 88 | damage_count | rectangles below that the page has still to upload: 0..8, or `0xffffffff` for all of the buffer |
| 92..220 | damage | up to 8 rectangles of x, y, w, h in buffer pixels (more than 8 are collapsed to their bounding box) |
| 224 | uploaded_id | page: the present whose damage it has uploaded |
| 228 | shown_id | page: the present it has drawn |
| 232, 236, 240 | desktop, shell_flags, tile | the window's desktop (1-based, 0 all), keep above/below, shaded, ... and its quick tile: PLASMA-PROTOCOL.md |
| 248, 252 | layer, role | a layer surface's layer; a window's role in Plasma's shell (PLASMA-PROTOCOL.md) |
| 244 | gpu_serial | format 2 only: the GPU server's `submitted` word when the buffer was committed (gpu/PROTOCOL.md) |
| 256 | title | 64 bytes of UTF-8, NUL-padded |
| 320 | app_id | 64 bytes of UTF-8, NUL-padded |

The damage in a slot is the union over all presents newer than `uploaded_id`
at the time the slot was written, so a page that falls behind by a present
misses nothing; a page that reads a slot while a newer one is being written
uploads a rectangle twice at worst.

## The screen

The screen is the page's: while a server runs, the page sizes `#screen` to
the window's width and the height left below its bar (`?screen=WxH` for a
fixed size; in fullscreen, the whole screen) and asks the server for that
size in CSS pixels with a scale of `devicePixelRatio` rounded
(`?scale=N` to choose), through the out_* words; the window's resizes follow,
150 ms after the last one. The server tells every client (`wl_output`
geometry, mode, scale and done; `zxdg_output_v1` logical size;
`wl_surface.enter` of the output when a surface is first shown; wl_compositor
6's `preferred_buffer_scale` on every surface) and fits the windows to it:
maximized and fullscreen ones take all of it (less the panel's strip, for
maximized ones), others are moved onto it and asked to be smaller when they
no longer fit (also when one is restored after the screen shrank), and new
ones are placed within it. The canvas has the server's screen times its
scale in pixels, so a client that draws at scale 2 (Qt does, told so) is
drawn pixel for pixel on a Retina screen; a scale-1 buffer is doubled
without smoothing; textures are smoothed only where the ratio is not a whole
number. Fractional scales (`wp_fractional_scale_v1`) are not offered: at a
devicePixelRatio of 1.25 the clients draw at 1 and the browser stretches the
canvas.

The kernel's frame buffer (surface 0, the text console) is not drawn while a
server runs: uploading its 3 MiB every frame was most of what the page
uploaded. `?console=1` draws it behind the windows, letterboxed.

A big screen at scale 2 means big buffers: a maximized window at 1440x900
on a Retina screen is 2880x1800x4 bytes, 20 MiB, which the kernel has to
find in one piece (a ramfs file grown from 0, see above).

## Looking at it without a browser

    DISK=wl HOOK=tools/wl-dump.js build/nm/run.sh 'debian "desktop wayland timeout 10 weston-simple-shm"'

`tools/wl-dump.js` (a `--hook` of `tools/node-machine.js`) listens for the
table, prints every slot as it changes, acknowledges presents the way the
page would, and writes each window's pixels as PNG files (`build/shots/`).

Environment the server reads: `WLSERVER_DEBUG=1` (every message),
`WLSERVER_STATS=1` (a line of counts every 5 s: turns, busy ms, presents,
damage bytes), `HOSTNODE_STRACE=1` (every system call).

Under node-machine there is no page to do things at the screen, so
wl-dump does them (`WL_DUMP_ACTIONS`, its header has the list): it moves the
pointer, clicks and types through the kernel's input ring the way the canvas
does (`os.screen_input`), writes orders and clipboard text into the table the
way the page does, and takes composed screenshots (`shot:NAME`). E.g.:

    WL_DUMP_MAX=0 WL_DUMP_DIR=build/shots-k WL_DUMP_ACTIONS='windows:1,150|settle:3|type:ls -la /\n|settle:2|shot:ls|rclick:400,300|wait:6|shot:menu' \
      DISK=wl HOOK=tools/wl-dump.js build/nm/run.sh 'debian "desktop wayland konsole & sleep 120"' 200000

## Input

The page puts what the person does into the kernel's input ring, as before,
and the kernel makes evdev events of it: /dev/input/event0 the keyboard,
/dev/input/event1 an absolute pointer (0..32767) with buttons and a wheel.
`seat.js` reads both (epoll, every turn; no EVIOCGRAB). The runtime raises
an interrupt when it puts events into the ring (tools/patch-runtime.py 13),
so they reach the kernel at once (they waited for a kernel thread that
looked every 3 to 6 ms, in fact every 10 to 20: the kernel's timers went by
its 100 Hz tick until the sched work).

The doorbell: /dev/input/event2, the kernel's "Wasm host" device (seat.js
checks the name), gives an `EV_MSC`/`MSC_SERIAL` event whenever the page
rings it (an input event of kind 5 through the same ring: `os.screen_input(5,
code, 0)`). The page rings once after anything it wrote into the table for
the server in a frame or an event: a present uploaded or shown (a changed
`uploaded_id` or `shown_id`), an order, the host's clipboard, a screen, a
layout, a piece of a file (display.js, `ringBell`). The server watches it
with the other descriptors, so those are seen within a turn's work instead
of at its next turn: frame callbacks and buffer releases go out as soon as
the page has shown and uploaded a present. With the doorbell there the
server's turns wait up to 50 ms; without it (an older kernel: no event2, or
one with another name) every 8 ms as before. The pointer goes to
the surface under it: windows from the top (popups are on top), each
subsurface above its parent, each surface's input region counting; while a
button is down it stays with the surface it went down on. A press on a
window that is not the active one activates it (raised, `activated` state,
the keyboard to it). The keyboard goes to the active window, or to the
newest mapped popup that asked for a grab; a press outside a grabbing
popup's client closes the popups (`popup_done`) and goes nowhere else.

`wl_keyboard`: the keymap is a file in `$XDG_RUNTIME_DIR` (unlinked), sent to
every keyboard, again to all of them when the layout changes; repeat is the
client's (25/s after 600 ms). Layouts are keymaps: the page sends physical
keys (evdev codes from `KeyboardEvent.code`), and the clients make
characters of them with the keymap (and their compose tables for dead keys:
`´` then `e` is `é` in `de`, `^` then `e` is `ê` in `fr`). What the server
keeps is the modifiers' state for the keymap in use (keyboard.js), read from
the keymap itself: each key's first symbol and the modifier map, with
xkb-data's compat rules for the keys that act (Shift, Control, Alt, Meta,
Super and Hyper set the modifiers of their key's map; ISO_Level3_Shift sets
LevelThree, whatever real modifier the keys of that symbol are mapped to,
Mod5 here; ISO_Level5_Shift LevelFive, Mod3; their _Latch and _Lock forms
latch or lock; Caps_Lock locks Lock, Num_Lock NumLock (Mod2), Shift_Lock
Shift). So the right Alt key is AltGr in `de`, `fr` and `us-intl`, and Alt in
`us`. Group switching and the rarer actions are not done (one layout per
keymap here).

The layout: `?kbd=NAME`, else what was last chosen in the bar's Keyboard
list (kept in the browser's storage), else a guess from
`navigator.keyboard.getLayoutMap()` (Chrome and Edge: which character each
key types), else `us`. The keymaps there are: us, us-intl, us-dvorak,
us-colemak, gb, de, de-nodeadkeys, ch, ch-fr, fr, be, ca, es, latam, it, pt,
br, nl, se, no, dk, fi, pl, cz, hu, tr, gr, ru, ua, jp (`keymaps/index.txt`;
`tools/wl-keymaps.sh` makes more). `wl_pointer`: enter, leave, motion, button, axis
(wheel: axis_source, axis_discrete, 15 per click), frame; version 7 of
`wl_seat`.

The pointer's picture: `wp_cursor_shape_v1` first (what Qt 6.8 uses): its
shape numbers go to the page, which shows the CSS cursor of the same name.
`wl_pointer.set_cursor` with a surface: the buffer is copied into a block
of the server's (read from the pool's file if the pool could not be mapped:
libwayland-cursor resizes its pool, see above, so such pixels can lag), and
the page makes a `url()` cursor of it.

## Windows and their frames

`xdg_toplevel`: configure with maximized, fullscreen, resizing and
activated; min and max size; `wm_capabilities` maximize, fullscreen,
minimize; `set_parent` (a dialog opens over the middle of its parent);
move and resize asked for by the client (`xdg_toplevel.move`/`resize`, as a
client-side title bar does) are done here by the pointer until the button
goes up. A configure is not sent while the client has not acknowledged the
last one: the newest wanted size goes when it does.

`xdg_popup` with `xdg_positioner`: anchor, gravity, offset, then within the
screen by the constraint adjustments in xdg-shell's order (flip, slide,
resize), relative to the parent's window geometry (so popups move with their
window), `reposition`, `grab`.

Decorations: `zxdg_decoration_manager_v1` (Qt) is always answered
`server_side`; `org_kde_kwin_server_decoration_manager` (GTK 3) defaults to
server and takes the mode the client asks for; a window that never asks is
framed too. Such a window has flag 32 in its slot, and the page draws its
frame in the DOM over the canvas (display.js, chrome.css): a title bar
(`title_height` above the window geometry) with minimize, maximize and
close, and a `border` to resize by (corners 10 pixels). A frame is clipped
(CSS clip-path) where windows above it cover it, so it neither shows nor
takes clicks there; where there is no frame the pointer goes through to the
screen and the kernel. Dragging the title bar sends move orders, dragging an
edge resize orders (one of each per frame at most), a double click maximize;
the server places the window (a resize from the left or top keeps the right
or bottom edge). Minimized windows are not drawn; the panel's task list has
them, to bring back.

## The panel, the switcher and the page's keys

The page draws a panel in a strip at the bottom of the screen (32 pixels,
`panel.css`; the screen request says how high, `out_panel`, and the server
keeps maximized and newly placed windows off it; a fullscreen window in
front covers it): **Apps**, a launcher of the programs the server found in
the guest's `.desktop` files (`/usr/share/applications`,
`/usr/local/share/applications`, `~/.local/share/applications`; those with
`NoDisplay`, `Hidden`, or `OnlyShowIn` without KDE left out; a filter box);
the **task list**, a button per window in the order they came, minimized
ones in italics (a click brings a window forward, restoring it if
minimized, or minimizes the one in front); and a **clock**. A program is
started by the launch order (10): the server takes the entry's `Exec`,
splits it into words by the Desktop Entry rules (quotes and escapes; field
codes such as `%f` and `%U` taken out; `Terminal=true` runs it in
`konsole -e`), and starts `desktop wayland WORDS...` with hostnode's
`hn_spawn` (clone with CLONE_VFORK, then exec; no shell sees the words, and
the page can name only an entry of the list, not a command). So the program
gets the environment and the session bus `desktop wayland` gives every
client, and joins this server. Its output goes to `/root/wlserver-apps.log`.
Icons are not shown (the entries' icon names are in the list; looking them
up in the icon themes is for the shell). Programs for X only (xterm, Dillo,
...) start too: `desktop wayland` gives every program `DISPLAY=:0`, and the
server starts Xwayland when the first X program connects (X programs,
below).

While a server runs, the keys on the screen go through the page, not the
runtime's handler, so that the page can keep some for itself:

| keys | what |
| --- | --- |
| Alt-Tab, Alt-Shift-Tab | the window switcher, the windows by recency (minimized ones too); Tab again goes on, letting go of Alt brings the one picked forward; Escape: none |
| Alt-` (the key above Tab), Ctrl-Alt-Tab | the same, for where the system takes Alt-Tab |
| Alt-F4 | close the active window (`xdg_toplevel.close`) |
| Meta-Left, -Right, -Up, -Down | KWin's quick tile of the active window: that half of the screen (the same key again: its size back) |

| on a Mac, Cmd-C, -V, -X, -Z, -A, -F, -T, -W, -N, -S, -O, -P, -R, -Y, -G | Ctrl with that key (Ctrl-Shift in a terminal for C, V, T, W, N, F: Konsole copies with Ctrl-Shift-C, and Ctrl-C would interrupt); Cmd with any other key is Super with it. When the switcher comes up, the guest is told that Alt, Ctrl, Shift and
Super went up (the keyboard is about to go to another window), and their
own release later goes nowhere. When the page loses the keyboard (another
window or tab in front), every key the guest has as down is let go.

What reaches the page at all depends on the browser and the system:

- macOS: Cmd-Tab, Cmd-Space, Cmd-Q, Cmd-H and Cmd-M are the system's;
  Option-Tab (Alt-Tab) and Option-F4 reach the page. Chrome keeps Cmd-W,

  and Super. Without fullscreen, use the bar, the panel, or whichever of

- The bar's **Fullscreen** puts the screen alone on the display and, in

## KWin's and plasmashell's parts: desktops, window states, rules, D-Bus

What KWin and plasmashell do besides drawing, the server does, so that KDE's
own tools work on it (PLASMA-PROTOCOL.md has what goes between the server and
the page; the page draws the pager, the effects, the popups):

- **Virtual desktops** (`desktops.js`): KWin's model (kwin 6.3,
  src/virtualdesktops.cpp): desktops with ids and names, the current one, a
  grid of `Rows` rows, moving left/right/up/down wrapping around when kwinrc
  `[Windows] RollOverDesktops` is true (KWin's default: false). Read from kwinrc `[Desktops]`
  (Number, Rows, Name_N, Id_N) at start and on reconfigure, written back as
  KWin writes it on every change. A window gets the current desktop when it
  maps (or a rule's, or the one an X program asked for with
  `_NET_WM_DESKTOP`); windows on other desktops get no input, their popups are
  closed, and activating one (the task manager, Alt-Tab) switches to its
  desktop. Changed by the page's orders, over D-Bus, and by X pagers.
- **Window states** (`shell.js`): keep above and keep below as KWin's layers
  (below < normal < above < the active fullscreen window < popups, in `z`);
  shade (the page draws the title bar only; the surface gets no pointer
  input); on all desktops; quick tiles (halves and quarters of the usable
  area; out of a tile the size from before comes back); "show desktop".
  X programs see and ask for them the EWMH way (`xwm.js`): `_NET_WM_STATE`
  ABOVE, BELOW, SHADED, STICKY, SKIP_TASKBAR, SKIP_PAGER, DEMANDS_ATTENTION
  (and WM_HINTS' urgency), `_NET_WM_DESKTOP`, and on the root
  `_NET_NUMBER_OF_DESKTOPS`, `_NET_CURRENT_DESKTOP`, `_NET_DESKTOP_NAMES`,
  `_NET_DESKTOP_LAYOUT`, `_NET_WORKAREA`, `_NET_SHOWING_DESKTOP`,
  `_NET_CLIENT_LIST(_STACKING)`, with their client messages.
- **The usable area**: the screen less the strips the page keeps for its
  panels on all four edges (out_panel at the bottom, out_strut_top/left/right);
  maximized and tiled windows fill it, new windows are placed in it, moved ones
  keep their title bar below the top strip, popups and fullscreen windows have
  the whole screen.
- **Window rules** (`rules.js`): `~/.config/kwinrulesrc` as KWin keeps it
  (System Settings' Window Rules page writes it): matching by window class
  (a Wayland window's app id, an X window's WM_CLASS in lower case; exact,
  substring or regular expression, or the whole "name class"), title, role
  (X's WM_WINDOW_ROLE) and window type; setting position, size, desktop,
  maximized (both directions), minimized, fullscreen, shade, keep above and
  below, no border, skip taskbar, pager and switcher. Carried out once, when a
  window first maps (an xdg toplevel: before its first configure, so a size
  rule is the first size it is asked for); "force" is not held against later
  changes, which is where this differs from KWin.
- **D-Bus** (`dbus.js`, a client of the session bus written from the D-Bus
  Specification: SASL EXTERNAL, Hello, RequestName, AddMatch, calls, returns,
  errors, signals, Properties and Introspectable; `WLSERVER_DBUS_DEBUG=1`
  logs every message): `kwin.js` is `org.kde.KWin` (`/KWin`: reconfigure,
  currentDesktop, setCurrentDesktop, nextDesktop, previousDesktop,
  showDesktop, ...; `/VirtualDesktopManager`: count, current, rows,
  navigationWrappingAround, desktops, createDesktop, removeDesktop,
  setDesktopName and their signals: all System Settings' Virtual Desktops page
  uses) and `org.kde.plasmashell` (`/PlasmaShell`: setWallpaper and wallpaper,
  which System Settings' Wallpaper page uses, and evaluateScript for the
  wallpaper statements of Plasma's scripting, which plasma-apply-wallpaperimage
  sends; the script is read as tokens, never run: it comes from any program of
  the session and this process has the page's powers). The wallpaper goes into
  `plasma-org.kde.plasma.desktop-appletsrc` as plasmashell writes it, which the
  page draws from; at start the server makes sure a desktop containment exists
  for the current activity (kactivitymanagerdrc), which the Wallpaper page
  needs. The server hears System Settings' `reloadConfig` signal as KWin does.
  `notify.js` is `org.freedesktop.Notifications` (spec 1.2: Konsole's,
  busctl's, GTK programs' notifications go to the page, which draws them, and
  its clicks come back as ActionInvoked) and `org.kde.StatusNotifierWatcher`
  (programs' tray items, read from them and sent to the page). `ksplash.js`
  is `org.kde.KSplash` (`/KSplash` setStage, as ksplashqml has it): the stages
  the session's programs name go to the page's splash screen
  (tools/www/splash.js), with the server's own (PLASMA-PROTOCOL.md: the splash

## The clipboard

`wl_data_device_manager` 3 and the primary selection work alike: the client
with the keyboard is offered the selection when it changes and when it gets
the keyboard; a `receive` is passed on to the source's client with the
descriptor, which the server then closes.

The host bridge, guest to host: when a client sets the clipboard with a text
type (`text/plain;charset=utf-8`, `text/plain`, `UTF8_STRING`, ...) the
server asks for the text at once through a pipe of its own and puts it in the
table (`guest_clip_*`); the page calls `navigator.clipboard.writeText`.
Host to guest: when the person presses Ctrl-V, Ctrl-Shift-V or Cmd-V on the
screen, the page holds the key back, takes the host's text (from the `paste`
event that key brings, or else `navigator.clipboard.readText()`), writes it
into the table (`host_clip_*`), waits for the server to make it the
selection (`host_clip_ack`), and then lets the key through (and the keys let
go meanwhile after it). Text that is what the guest itself last copied is
not sent back, so the guest's own selection keeps its other types.

What browsers allow, and when:

- `writeText` needs a focused document; Chrome grants it to a focused page
  of a secure origin (localhost counts) without asking; Firefox and Safari
  want a user activation, which the copy keystroke gives for about five
  seconds (the text usually reaches the table well within that). A write the
  browser refuses is tried again on the next key or click on the page.
- A `paste` event comes with the text and needs no permission, but only for
  the platform's paste key: Ctrl-V on Linux and Windows, Cmd-V on a Mac (a
  Mac's Ctrl-V and Ctrl-Shift-V bring none). Without one the page calls
  `readText()`, which Chrome lets a page do only after the person allowed it
  (a prompt the first time), and Firefox only from a paste the person chose.
- On a Mac, Cmd-V is Ctrl-V (Ctrl-Shift-V in a terminal) for the guest, and
  the platform's paste key for the browser, so it brings a `paste` event:
  no permission is needed.

## X programs

Two ways, both through the server:

    debian desktop x11 xterm           rootless: each X window a window of ours
    debian desktop wayland-x xterm     rootful: all of X in one window, twm in it

**Rootless** (`xwm.js`, `x11.js`, `xselection.js`). At start the server
makes X's socket `/tmp/.X11-unix/X0` (and the lock `/tmp/.X0-lock`) and
only watches it (`WLSERVER_X=0`: not even that; a live X server that holds
the lock already: neither). When an X program connects, the server starts
`Xwayland :0 -rootless -shm -wm 4 -listenfd 5 -terminate 30` with
`hn_spawn` (hostnode.c): descriptor 5 is that socket, so Xwayland accepts
the program that was waiting; 3 (`WAYLAND_SOCKET`) is one end of a socket
pair whose other end is a client of the server (`addClient`, marked
`xwayland`: the only client that sees the `xwayland_shell_v1` global); 4 is
one end of another pair, on which Xwayland makes a client for the window
manager, and the server speaks X11 on the other end. Xwayland's output goes
to `/root/xwayland.log`. It ends itself 30 seconds after its last X program
(`WLSERVER_X_LINGER`), the server sees it go (apps.js reaps its children)
and watches the socket again; a server that fails three times in 30
seconds is not started again. `desktop wayland` gives every program
`DISPLAY=:0`, so X-only programs work from it and from the launcher; Qt and
GTK programs stay on Wayland (Qt is told `QT_QPA_PLATFORM=wayland`, GTK 3
tries Wayland first). `desktop x11 PROGRAM` makes a program an X one
(`GDK_BACKEND=x11`, `QT_QPA_PLATFORM=xcb`, `MOZ_ENABLE_WAYLAND=0`, no
`WAYLAND_DISPLAY`).

The window manager, in order: it takes the window manager's selection
`WM_S0` (Xwayland given `-wm` accepts no programs on its `-listenfd`
sockets before someone has), selects SubstructureRedirect on the root,
redirects the root's children (Composite, manual: rootless Xwayland makes a
`wl_surface` only for windows so redirected), sets `_NET_SUPPORTED` and
`_NET_SUPPORTING_WM_CHECK`, and asks XFIXES about the selections. Then:

- A window and its surface are matched by a serial that Xwayland gives both:
  `xwayland_surface_v1.set_serial` on the Wayland side, a `WL_SURFACE_SERIAL`
  client message on the X side (or, from an Xwayland without
  `xwayland_shell_v1`, `WL_SURFACE_ID` with the surface's object id). They come
  on two sockets in either order; the surface is shown once both have come
  and the window is mapped. A surface that drew before that is shown as it
  is (compositor.js `showCurrent`), and buffers it drew meanwhile are
  released.
- `MapRequest`: the window's properties are read (`WM_NAME`/`_NET_WM_NAME` for
  the title, `WM_CLASS` for the app id, `WM_NORMAL_HINTS`, `WM_HINTS`,
  `WM_PROTOCOLS`, `WM_TRANSIENT_FOR`, `_NET_WM_WINDOW_TYPE`, `_NET_WM_STATE`,
  `_MOTIF_WM_HINTS`, `_GTK_FRAME_EXTENTS`), `WM_STATE` and `_NET_FRAME_EXTENTS`
  set, and it is mapped. Changes to those properties later are read again.
- A toplevel goes through shell.js like an xdg toplevel: placed down the
  staircase (a `WM_TRANSIENT_FOR` dialog over its parent; a window whose hints
  say USPosition/PPosition where it asks), framed by the page (unless
  `_MOTIF_WM_HINTS` say no decorations, or `_GTK_FRAME_EXTENTS` say it draws
  its own frame, whose shadows are then outside its window geometry),
  activated, moved, resized, maximized, made fullscreen, minimized and closed
  by the page's orders. Where an xdg toplevel would get a configure, an X
  window gets a ConfigureWindow (its size within `WM_NORMAL_HINTS`: minimum,
  maximum, base and increments, so xterm grows by whole characters). A program's
  own ConfigureRequest is done for its size; its position is ours once it is
  mapped; a request that changes nothing is answered by a synthetic
  ConfigureNotify (ICCCM 4.1.5).
- Override-redirect windows (menus, tooltips) and windows whose
  `_NET_WM_WINDOW_TYPE` is a menu, tooltip, notification, combo or drag
  icon are popups: kind 2 in the table, where X has them, above the windows,
  no frame, no focus. X programs grab the pointer for their menus inside X;
  the pointer stays with the window a button went down on until it goes up
  (seat.js), and that is all an X menu needs.
- Coordinates: X's root is our screen, pixel for pixel, at scale 1 (Xwayland
  draws at scale 1; on a Retina screen the page doubles it). An X window is
  kept at the place we draw it: whenever its slot is written and its place
  changed, the X window is moved (`xwmSync` from writeSlot), so that
  Xwayland's pointer coordinates and the places X programs work out for
  their menus are right.
- Focus: an activated X window gets X's input focus (SetInputFocus, unless
  its `WM_HINTS` say it takes none; `WM_TAKE_FOCUS` if it asks for that), is
  raised among the X windows, and is `_NET_ACTIVE_WINDOW`; an activated
  Wayland window takes X's focus away (focus None). The keyboard itself
  reaches Xwayland as for any client (`wl_keyboard.enter` on the window's
  surface).
- `_NET_WM_STATE` is kept as the window is (maximized vert+horz, fullscreen,
  hidden, focused), and `WM_STATE` iconic or normal. Client messages:
  `_NET_WM_STATE` (add, remove, toggle maximized, fullscreen, hidden),
  `_NET_ACTIVE_WINDOW`, `_NET_WM_MOVERESIZE` (a GTK window dragged by its own
  title bar: the pointer moves or resizes it, seat.js's grab),
  `WM_CHANGE_STATE` to iconic (minimize), `_NET_CLOSE_WINDOW`. Our close
  button sends `WM_DELETE_WINDOW`, or KillClient for a window that does not
  take it.

The clipboard between X and Wayland (`xselection.js`), `CLIPBOARD` and
`PRIMARY` both: when an X program takes a selection (XFIXES tells us), we
ask it for `TARGETS` and make the Wayland selection ours with the types
those give (`UTF8_STRING` is `text/plain;charset=utf-8`, `STRING` and `TEXT`
are `text/plain`, targets whose names have a slash are those MIME types);
a Wayland client's `receive` (and the host bridge, which then copies X's
text to the host) is a ConvertSelection, the property read and written into
its descriptor (INCR, X's way for big data, followed). When the Wayland
selection is a Wayland client's or the host's, our window owns the X
selection, and an X program's `SelectionRequest` gets `TARGETS`,
`TIMESTAMP` or the data, read from the Wayland source through a pipe and
put on its property in pieces of 128 KiB appended to one property (no INCR
this way), then `SelectionNotify`. `MULTIPLE` is refused.

Not done for X programs: drag and drop between X and Wayland programs
(XDND); `_NET_WM_SYNC_REQUEST` (a resize does not wait for the program to
have drawn); `_NET_WM_ICON`; keyboard grabs (`zwp_xwayland_keyboard_grab`); pointer
constraints and relative motion (games).
`WLSERVER_XDEBUG=1` logs every X event the window manager gets and every
error of its requests.

**Rootful** (`desktop wayland-x [PROGRAM]`, tools/x/desktop): `Xwayland :1
-shm -geometry WxH` as one xdg toplevel of the server, its size from
`$XDG_RUNTIME_DIR/wlserver.screen` (the screen less our frame and the
panel's strip; the server writes the file once the page has said its
screen, or two seconds after start without a page, and on every change),
twm in it, then PROGRAM (xterm) with `DISPLAY=:1`; another `desktop
wayland-x PROGRAM` while it runs joins it. Resizing the window from our
frame resizes X's screen (Xwayland 24 follows the toplevel's configure),
maximizing too. What Xwayland and twm print goes to `/root/xwayland.log`.

## Drag and drop

Between windows (`drag.js`): `wl_data_device.start_drag` with a button down
gives the pointer to the drag until the button goes up (no client gets
`wl_pointer` events; the page shows a copy cursor, from the `drag` word);
the client under the pointer gets a `wl_data_offer` of the source (its types
and `source_actions`) with `enter`, `motion` and `leave`; what it says
(`accept`, `set_actions`) goes back to the source (`target`, `action`, the
action both can do, its preferred one if it can). The button let go over a
client that accepted a type, with an action agreed: `drop` (and
`dnd_drop_performed`), then `receive` is passed to the source like a paste
and `finish` is `dnd_finished`; anywhere else: `leave`, and `cancelled`. A
drag with no source stays within its client. The icon surface is a slot of
kind 5 at the pointer plus its offset, drawn by the page above everything.

From the host: files dropped on the screen from the person's desktop are
written into the guest's `~/Downloads`. The page cannot write the guest's
files, but the server can (it is a process of the machine): the page hands
each file over in pieces of 4 MiB through a block of the server's memory
(the `xfer_*` words) and waits for each piece to be written. The name is the
file's own reduced to a plain name (no directories, no leading dots, no
control characters, 200 bytes at most); a name that is taken gets a number
(`name (1).txt`); files are created and never overwritten (O_EXCL); at most
512 MiB a file and 1 GiB a drop. Dropped onto a window, the files are then
offered to that window as a drop of the server's own (`text/uri-list` with
`file://` URIs, and `text/plain` with the paths), at the place they were
dropped: the drop follows the window's `accept`, or 400 ms. Folders are not
taken (the browser gives no contents for them).

Out of the page to the host's desktop: not done, and not feasible as things
are: a browser starts a drag to the outside only from a mouse press on a
draggable element of the page itself, while a guest's drag is begun by the
guest from events the page already passed on.
